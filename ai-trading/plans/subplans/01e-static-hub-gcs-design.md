# Release 1 Design Addendum: Static Hub in GCS, APIs on VPS

Status: Approved by owner on 2026-10-05. Paired with [the unmodified MiroFish design](01d-mirofish-hub-design.md). This changes how the hub and the original MiroFish Vue UI are delivered; TradingAgents, ai-hedge-fund, and Vibe-Trading runtime UIs remain on the VPS.

## Goal and boundary

Build the Trading Hub and MiroFish's **original Vue frontend** as client-side static files in dedicated GCS buckets in `tobytran-portfolio`. Host no Next.js runtime, Flask API, Clerk session verifier, or database in GCP. The GCP buckets store only built HTML/CSS/JS, **never secrets, accounts, uploads, or portfolio data**. TradingAgents and ai-hedge-fund remain VPS browser terminals; Vibe-Trading remains its original VPS web UI. Family Desk's future API and MiroFish's Python backend and local files stay on the VPS; MiroFish's graph memory necessarily uses external Zep Cloud.

## Next.js export

- Change the existing hub from `output: "standalone"` to `output: "export"`. Its `generateStaticParams()` already lists dynamic app slugs, and all current pages use static registry data. Build produces `out/index.html`, app-page HTML, `out/404.html`, and `_next/static` assets. No Next.js server container is needed in production.
- No middleware/proxy, server-side Clerk helpers, runtime `cookies()`/`headers()`, API routes, rewrites, redirects, Server Actions, or ISR in this static app. Client components call the VPS API and use a client-side Clerk SDK for Google login. The Clerk publishable key may be embedded in the static bundle; the Clerk secret key, OpenAI key, and Zep key may not. Google's OAuth provider must already be configured on the production Clerk instance used by the sibling expense app.
- The launcher lives in this static export. MiroFish's **unchanged Vue app** is built separately from `packages/mirofish/frontend/` into a second bucket with `VITE_API_BASE_URL=https://mirofish.tobytran.dev` baked at build time. The hub page links to that original UI only after its backend, keys, and auth gate pass an activation check. Preserve the current hub routes and terminal-iframe URLs.

## HTTPS and same-origin routing

The [Google Cloud Storage documentation](https://cloud.google.com/storage/docs/hosting-static-website) says a GCS bucket **cannot provide custom-domain HTTPS on its own**; Google's example adds a billable external HTTPS load balancer. Avoid that load balancer for this family app. Use Cloudflare's edge Worker as a **routing layer**, not the application backend:

1. Terraform provisions **two dedicated public-read-only static buckets** (hub and MiroFish UI, separate from Terraform state/backups) and a CI identity allowed to upload assets only to them. A reviewed build uploads `ai-trading/frontend/out/` to the hub bucket and the unmodified submodule's `frontend/dist/` to the MiroFish bucket. Deploy hashed assets with long immutable cache headers; HTML/404 get short/no cache. A public asset URL is acceptable because the files contain no private data.
2. Cloudflare Worker routes on `trading.tobytran.dev/*` and `mirofish.tobytran.dev/*` serve static GET/HEAD paths from their respective GCS buckets over HTTPS. The hub route maps `/` to `index.html`, known app routes to exported HTML and other paths to `404.html`; the MiroFish route supports Vue history-mode deep links by falling back to its `index.html`. Do not treat GCS public-read access as protection for private user data.
3. Terraform creates two **unrouted tunnel-origin hostnames**, `trading-origin.tobytran.dev` and `mirofish-origin.tobytran.dev`, on the existing ai-trading tunnel, with no Worker route on either one. The `trading.tobytran.dev` Worker forwards `/u/tradingagents/*`, `/u/ai-hedge-fund/*`, `/__auth/*`, `/__control/*` (the post-MVP settings phase), and future dynamic API paths to the same path on `trading-origin.tobytran.dev`; the `mirofish.tobytran.dev` Worker forwards `/api/*` to the same path on `mirofish-origin.tobytran.dev`. Construct a new Request with that URL and forward the original method, body, cookies, and WebSocket Upgrade headers; return the origin response, including a 101 WebSocket response, without parsing it. The separate origin hostnames prevent Worker recursion. **Probe ttyd WebSocket reconnect and MiroFish multipart uploads before replacing the current Next server.** No business logic, LLMs, or persistent state runs in the Worker.
4. The static hub uses Clerk's client-side SDK for Google login. After Clerk issues a session token, it POSTs it in an `Authorization: Bearer` header to same-origin `/__auth/session`. A small VPS verifier validates Clerk JWT signature, issuer, audience and authorized party against Clerk JWKS, checks the family allowlist, then issues a short-lived signed `Secure; HttpOnly; SameSite=Lax; Domain=tobytran.dev` gateway session cookie. The browser never stores a backend key. Caddy uses `forward_auth` to this verifier and its built-in reverse proxy for HTTP and WebSocket requests; do not write a custom WebSocket proxy. That cookie works for requests to both family subdomains, terminal iframes, and WebSockets. The gateway rejects invalid sessions and non-allowed Origins for write requests, strips client-supplied identity headers, sets the verified ttyd user itself, and protects **every** backend request including `/api/*` and WebSocket upgrades. MiroFish's Flask CORS `*` is not authentication.
5. Before serving MiroFish's Vue HTML at the custom hostname, the Worker calls `GET https://mirofish-origin.tobytran.dev/__auth/check` with the visitor's gateway session cookie. The VPS verifier returns 204 for an allowed user, otherwise redirects to `https://trading.tobytran.dev/login` with a return URL. The Worker relays that response. This login redirect improves UX; direct public GCS asset URLs remain readable because **only the backend contains private data**, and the VPS gateway is the actual security boundary. The direct `mirofish-origin.tobytran.dev` hostname also passes through that gateway; it must never bypass authentication.

The existing expense Clerk production instance and its Google login serve the hub. Begin with a small ai-trading verifier; extract into `common/auth/` only if both apps can actually consume the same abstraction without changing expense behavior or expanding its Docker build context speculatively.

If the Worker cannot reliably forward WebSockets or signed-in requests to the tunnel, keep `output: "export"` but serve the same built assets from a tiny static server on the VPS behind the current tunnel. The built artifact still lands in GCS, but **the VPS becomes the serving origin** until a working GCS edge route is demonstrated. Do not reintroduce Next.js SSR just for static pages. This fallback needs user review because it departs from GCS-origin serving.

## Infrastructure and verification

- Infrastructure-as-code lives under shared `infrastructure/gcp/ai-trading/` (both static buckets and upload IAM) and `infrastructure/cloudflare/ai-trading/` (both Worker routes and tunnel ingress). App build/deploy scripts live in `ai-trading/deploy/`. No Cloud Functions or Cloud Run are required for this design.
- CI confirms the hub export contains home, four upstream app routes, and a 404 page and the MiroFish Vue build emits an `index.html` and assets. Neither static bundle may contain provider secrets or private holdings. Test edge path mapping (hub routes, Vue deep link, hashed assets, 404, backend API, terminal WebSockets), direct origin-hostname requests without authentication, and `/__auth/check` before applying DNS changes. Browser checks run at 375, 768, 1024, and 1440 px, including keyboard and iPad login.
- Deployment order: publish the static build to GCS, verify its assets, provision/test the Worker on a staging hostname, confirm the existing tunnel routes and Clerk gateway, then switch `trading.tobytran.dev` to Worker-backed delivery. Keep the current VPS web container until the cutover passes health and rollback checks. A failed cutover restores the current tunnel route without changing backend state.
- MiroFish's original Python backend needs `LLM_API_KEY` (an OpenAI-compatible model) and `ZEP_API_KEY` (Zep Cloud). Runtime values come from the pending Firestore `family-config` handoff, not from either static build and not from a new Secret Manager bundle.

## Non-goals

No GCP compute for the app, no frontend secrets, no full rewrite of the other three upstream UIs, no anonymous Flask API exposure, and no paid GCP load balancer without an explicit cost decision.
